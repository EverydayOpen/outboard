How to move Xcode DerivedData to an external drive

The short answer

  1. Xcode has a setting for it: Settings › Locations › Derived Data › Custom. The same choice is stored in the com.apple.dt.Xcode defaults domain.
  2. DerivedData rebuilds itself, so losing it costs build time, not your work.
  3. Two problems are documented on external drives, so try it, and keep what you have until you are sure it works.

What DerivedData is

Build products and indexes that Xcode writes under ~/Library/Developer/Xcode/DerivedData. Community guides and forum posts put it anywhere from 5 to 100 GB; those are reports, not an Apple figure, so measure your own. It is regenerable: Xcode builds it again when it is missing, which is why it is the lowest-stakes of the Xcode moves.

The official way

In Xcode, open Settings › Locations. Next to Derived Data choose Custom and pick a folder on the drive. The path is stored under the key IDECustomDerivedDataLocation in the com.apple.dt.Xcode defaults domain, which is where tools such as fastlane read it.

A second key, IDEDerivedDataPathMode, decides how that path is read. We could not find a source that says which value means "an absolute custom path", so this guide does not print one. If you script the change, set the folder once in the Locations pane and read what Xcode wrote with defaults read com.apple.dt.Xcode. For a single build there is also xcodebuild -derivedDataPath with a folder.

Quit first

Quit Xcode, Simulator and Instruments, and stop any xcodebuild that is running, before you change the setting or move the folder.

Known breakages

  • Framework tests on "My Mac" fail with exit code 9 when DerivedData is on an external drive, and Xcode gives no warning (Apple Developer Forums, thread 812321).
  • Swift package build plugins fail with "Operation not permitted" when DerivedData is a custom external path (swift-package-manager issue 6948, reported on Xcode 15 with Swift 5.9, still open when we checked).

In both reports, running xcodebuild from Terminal, or using the default location, avoids the failure. We have not checked either one on Xcode 26 or 27, so treat them as things that may still happen.

What Outboard does

Outboard copies the DerivedData folder to your drive, compares every file with the original by size and SHA-256, writes the same setting Xcode's Locations pane writes, and keeps your original as DerivedData.before-move until you confirm. If the drive is away and Xcode is closed, it writes the setting back so Xcode uses its normal folder; when the drive is back and Xcode is closed, it points the setting at the drive again.

It is the first move in the rollout. It stays hidden in the app until a tester's entry is in the verify log, and its sheet says so. Not yet tried on a real Mac. What the sheet tells you before you start:

  • Xcode can rebuild this folder, so losing it costs build time, not your work.
  • While Outboard is running, it puts the setting back if your Outboard drive is unplugged, so Xcode uses its normal folder on your Mac and builds start from scratch there. It points the setting at the drive again when the drive returns and Xcode is closed. If Xcode is open when the drive is unplugged, the setting is not changed until you quit Xcode, so until then Xcode still points at the missing drive.
  • Your original stays as DerivedData.before-move until you confirm. You can roll back until then.
  • Some developers report that tests for macOS frameworks, and Swift package plugins, fail when DerivedData is on an external drive (Apple Developer Forums, Swift Package Manager issue 6948). If that happens, roll back.

Archives are different

Archives hold the builds you shipped, with their debug symbols. Xcode cannot rebuild them into the same thing, so they are not regenerable. Their key is IDECustomDistributionArchivesLocation, and Xcode does not migrate existing archives for you. Outboard treats them as "Can't be replaced": the consent sheet makes Cancel the default button, says that Time Machine may not back up the drive, and the move is the last one in the rollout.

What can't move

Simulator runtimes are disk images that Xcode manages. People report simulators failing to load after a link or an alias to an external CoreSimulator folder (Apple Developer Forums, read through search summaries only, so low confidence). Apple's own routes are removing runtimes you don't need in Xcode › Settings › Components, or saving one for later with xcodebuild -downloadPlatform iOS -exportPath and restoring it with xcodebuild -importPlatform. Outboard lists simulator runtimes as not offered.
